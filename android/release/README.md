# Android release candidate

This workflow builds and verifies a candidate. It does not upload or publish it.

Use Flutter **3.47.1** and Java **17 or later**. CI uses Temurin 17. Keep the
Flutter pin in `build.py` and `.github/workflows/mobile-release.yml` together.
Dependencies resolve from the committed `pubspec.lock` with `--enforce-lockfile`.

## Private configuration

- Restore the existing upload keystore and ignored `android/key.properties`
  using `android/key.properties.example` as the template. Relative `storeFile`
  paths resolve from `android/app`, as they do in Gradle. Do not commit these files.
- Put the restricted Android Maps key in ignored `android/local.properties` as
  `MAPS_API_KEY=...`. The packaged-key check proves presence, not correct Cloud
  Console restrictions. Test Maps with the final Play-signed installation too:
  its app-signing certificate can differ from the upload certificate.
- Select the version and a build number not previously used in Play Console.
  The script cannot determine previously uploaded build numbers.

Do not replace an existing application's upload key without checking its Play
Console configuration. No key is generated by this workflow.

## Build locally

From the repository root:

```sh
python3 android/release/build.py --check-only \
  --version 1.0.0 --build-number 1 \
  --api-url https://chetiwa-api.ezplatforms.com

python3 android/release/build.py \
  --version 1.0.0 --build-number 1 \
  --api-url https://chetiwa-api.ezplatforms.com
```

The version/build values above are examples, not a reservation in either store.
Complete `flutter analyze` and the app tests before the build; CI requires them.
`--verify-only` rechecks an existing release AAB against the supplied version and
the configured upload certificate, without rebuilding it. It checks bundle
structure, manifest and signatures; it cannot recover Dart build defines or
prove which API endpoint or environment was compiled into an existing artifact.
Its `--api-url` input is validated but is not evidence of the artifact's endpoint.

The build uses the production environment, the selected HTTPS API origin and
disabled direct-provider fallback. It validates the AAB with checksum-pinned
Google bundletool, verifies every payload is signed by the configured non-debug
upload certificate, and checks package, version, target SDK (at least 36), Maps
key presence and non-debuggable status. Certificate validity is also checked.

Outputs:

- `build/app/outputs/bundle/release/app-release.aab`
- `build/app/outputs/bundle/release/release-verification.json`, including the AAB
  digest, public certificate fingerprint, tool versions and source revision.

The signature check does **not** prove that Play Console recognizes this upload
certificate. The report also does not prove runtime behavior, provider rights,
16 KB native-library compatibility, or completion of store declarations. Those
remain release checks. A dirty-source indicator records local changes; release
CI should run from the reviewed commit containing all intended fixes. The source
revision and dirty indicator do not identify or prove inclusion of individual
uncommitted changes; the AAB digest identifies the resulting artifact.

## CI secrets

The manually dispatched workflow requires `ANDROID_KEYSTORE_BASE64`,
`ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_PASSWORD`, `ANDROID_KEY_ALIAS`,
`GOOGLE_MAPS_ANDROID_API_KEY`, `GOOGLE_MAPS_IOS_API_KEY` and
`CHETIWA_API_BASE_URL`. Secret presence in the repository is not evidence they
are configured in GitHub. The iOS job remains explicitly **unsigned** and needs
a separate App Store distribution/archive process.

## Check the release tooling

```sh
python3 -m unittest discover -s android/release -p 'test_*.py'
```

These tests generate temporary test-only certificates, then check that the
verifier rejects unsigned, tampered, partially signed and wrongly signed
payloads. They never access or create a production upload key.
